# Architecture

## Stack

| Layer | Technology | Rationale |
|---|---|---|
| Framework | Astro 5 | Ships zero JS by default; islands for interactivity; native content collections |
| Interactivity | React (islands only) | Familiar, well-supported, isolated to components that genuinely need it |
| CMS | Prismic | Headless, TypeScript SDK, Slice Machine, good DX for solo maintainers |
| Styling | Tailwind CSS 4 | Utility-first, co-located styles, minimal runtime |
| Language | TypeScript (strict) | Type-safe CMS queries and component contracts |
| Deployment | Vercel | Zero-config Astro adapter, ISR support, analytics |

## Rendering Strategy

| Page | Strategy | Rationale |
|---|---|---|
| Home | SSG | Static, rarely changes |
| Work | SSG | Case Study list is build-time |
| Case Study Detail | SSG + ISR | Content-driven; revalidate on Prismic webhook |
| About | SSG | Changes infrequently |
| Insights | SSG + ISR | List revalidates when new Insight published |
| Insight Detail | SSG + ISR | Same as Case Study |
| Contact | SSG | Contact info lives in Settings singleton |
| 404 | SSG | Static error page |

ISR (Incremental Static Regeneration) is triggered via Prismic webhook → Vercel deploy hook on content publish. No polling.

## Project Structure

```
src/
  components/
    ui/              # Design system primitives — Button, Tag, Badge, Link, etc.
    shared/          # Shared page-level compositions — SectionHeader, RichText, CodeBlock, etc.

  features/
    home/            # Hero, FeaturedWork, InsightsPreview, AboutSnippet, HomeCTA
    work/            # CaseStudyCard, WorkList
    case-study/      # Slice renderers: Problem, Architecture, Implementation, Results, Reflection
    about/           # AboutLead, Timeline
    insights/        # InsightCard, InsightList
    contact/         # ContactInfo

  islands/           # React components requiring client-side hydration
                     # Each file must have a comment explaining why it needs to be an island

  layouts/           # Astro layout wrappers (BaseLayout, PageLayout)

  pages/             # File-based routing only — minimal logic, delegates to feature components
    index.astro
    work/
      index.astro
      [uid].astro
    about.astro
    insights/
      index.astro
      [uid].astro
    contact.astro
    404.astro

  lib/
    prismic.ts       # Typed query helpers (getSingle, getCaseStudy, getAllInsights, etc.)
    seo.ts           # Meta tag and structured data builders

  prismicio/
    client.ts        # Prismic client instance
    types.ts         # Generated by prismic-ts-codegen — DO NOT edit manually

  styles/
    global.css       # Tailwind base layer + CSS custom properties (design tokens)

  env.d.ts

docs/                # Project documentation
public/              # Static assets: favicon, robots.txt, default OG image
```

### Why feature-based, not layer-based

The initial structure organized components into `ui/`, `layout/`, and `sections/`. The `sections/` directory is where this breaks down: it becomes a flat bucket for everything that isn't a primitive, making it impossible to distinguish shared components from page-specific ones.

The feature-based structure solves this specifically for **slice renderers**. A `Problem.astro` slice renderer for Case Studies belongs inside `features/case-study/`, not alongside `Hero.astro` in a generic `sections/` directory. Co-locating feature-specific components with their feature makes the codebase navigable without a mental map.

Pure UI primitives (`Button`, `Tag`, `Badge`) and shared compositions used across multiple features (`SectionHeader`, `RichText`, `CodeBlock`) stay in `components/` — they are genuinely cross-cutting. The feature directories hold only what is specific to that feature.

This structure adds no meaningful overhead for a solo project and scales naturally if Case Studies or Insights grow in complexity.

## Data Flow

```
Prismic CMS
    │
    ▼
src/prismicio/client.ts  (typed client)
    │
    ▼
src/lib/prismic.ts  (query helpers with typed return values)
    │
    ▼
src/pages/*.astro  (getStaticPaths / Astro.props)
    │
    ├── feature components  (SSG output, Astro)
    └── src/islands/*.tsx   (hydrated client-side where needed)
```

Pages are responsible for fetching data. Feature components are responsible for rendering it. No component fetches its own data.

## Component Philosophy

- **Astro components** are the default. No JS overhead.
- **React islands** are used only when the component requires stateful interactivity. Each island file must include a comment explaining the justification.
- Props flow down from pages. No global state libraries.
- No CSS-in-JS. All styles via Tailwind utility classes or CSS custom properties in `global.css`.
- Components in `features/` receive typed Prismic slice/document data as props. Components in `components/ui/` and `components/shared/` receive plain typed props only — no Prismic dependencies.

## TypeScript Configuration

- `strict: true`
- Path aliases: `@/*` → `src/*`
- Prismic types generated via `prismic-ts-codegen` — run after any schema change
- Generated types committed to `src/prismicio/types.ts`

## Environment Variables

| Variable | Required | Purpose |
|---|---|---|
| `PRISMIC_REPOSITORY_NAME` | Yes | Prismic repo identifier |
| `PRISMIC_ACCESS_TOKEN` | No (public repo) | Required if repo is set to private |

## Deployment

- **Host**: Vercel
- **Adapter**: `@astrojs/vercel` with `output: 'static'`
- **Rendering**: all pages are statically generated at build time. Content changes are deployed through Vercel rebuilds — no polling, no on-demand rendering.
- **Deploy triggers**: git push to `main`, Prismic publish webhook
- **Preview deploys**: Vercel branch previews on all PRs
- **Domain**: `portfolio.farrel.tech`

## Performance Targets

- Lighthouse Performance ≥ 95 (all pages)
- Lighthouse Accessibility = 100
- Core Web Vitals: LCP < 2.5s, CLS < 0.1, INP < 200ms
- Total JS shipped to client: < 50kb gzipped (excluding React island bundle on pages that need it)
- No render-blocking resources
